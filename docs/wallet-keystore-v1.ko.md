# GPUChain 개인키 암호화 및 복구 설계

**구현 상태.** 기존 Ed25519 서명 키의 암호화 백업, 검증, 동일 주소 복구가 구현됐다. 현재 노드가 상시 서명에 쓰는 지갑은 기존 JSON 형식이다. 아래의 24단어 기반 신규 키 생성과 상시 지갑 파일 잠금은 설계 단계다. [현재 사용 가능한 백업 및 복구 절차](wallet-backup.md)

## 설계 목표

지갑 파일을 복사한 사람이 곧바로 송금하지 못하게 하고, 소유자는 PC를 잃어도 기존 주소의 서명 권한을 복구할 수 있게 한다. GPUChain 주소는 지금처럼 Ed25519 공개키 32바이트의 소문자 16진수 표현이다. 공급자가 번 코인도 같은 주소에서 쓴다. 암호화 파일과 복구 정보는 로컬 지갑에만 속하며, 원장에는 공개 주소와 서명만 필요하다. [현재 키·서명 코드](../src/crypto.mjs)

Bitcoin Core에서 참고한 부분은 **비밀번호로 임의의 암호화 키를 보호하고, 그 키로 지갑 비밀을 보호하는 구조**다. GPUChain의 파일 포맷, scrypt 설정과 AES-GCM 선택은 이 프로젝트의 설계 결정이다. 복구 문구는 별도로 BIP39를, Ed25519 파생에는 SLIP-0010을 따른다. GPUChain 복구에는 GPUChain용으로 새로 만든 문구를 사용한다. [Bitcoin Core 지갑 암호화 소스](https://github.com/bitcoin/bitcoin/blob/master/src/wallet/crypter.h) · [BIP39](https://bips.dev/39/) · [SLIP-0010](https://github.com/satoshilabs/slips/blob/master/slip-0010.md)

## 키 생성

| 단계 | v1 규칙 |
|---|---|
| 복구 문구 | 운영체제 암호학적 난수 생성기로 지갑마다 독립적인 256비트 엔트로피를 만들고 BIP39 영문 목록과 체크섬으로 24단어를 생성한다. 사용자가 직접 고른 문장은 허용하지 않는다. |
| 복구용 시드 | 영문 목록과 체크섬을 검증한다. 표준 BIP39의 UTF-8 NFKD, PBKDF2-HMAC-SHA512, 2,048회, 64바이트 출력을 사용한다. 추가 BIP39 패스프레이즈는 빈 문자열로 고정한다. 파일 잠금 비밀번호는 이 계산에 들어가지 않는다. |
| 서명 키 | SLIP-0010 Ed25519로 고정 경로 `m/1196447043'/0'`의 32바이트 자식 키를 파생한다. 두 단계 모두 hardened다. 첫 인덱스는 ASCII `GPUC`의 정수값이고, 이 경로는 GPUChain v1의 자체 규약이다. |
| 주소와 보관 | 자식 키를 Ed25519 서명 시드로 사용해 공개 주소를 계산한다. 파일에는 이 **32바이트 자식 키 하나**를 암호화한다. 문구와 상위 파생 키는 최초 백업 확인 후 메모리에서 해제한다. |

사용자·공급자·시퀀서가 서로 다른 지갑을 만들면 각각 독립된 문구를 받는다. 역할명이나 파일명이 파생 경로를 바꾸지 않는다. 어느 한 역할의 복구 문구로 다른 역할의 키를 얻을 수 없다. 각 문구는 해당 지갑의 공개 주소와 함께 오프라인으로 보관한다. 생성 화면에서 재입력으로 백업을 확인한 뒤 초기화를 완료한다. [BIP39 생성 및 시드 변환](https://bips.dev/39/) · [SLIP-0010 Ed25519 파생](https://github.com/satoshilabs/slips/blob/master/slip-0010.md)

## 파일 형식과 암호화

파일은 아래 네 필드로 구성한 UTF-8 JSON이다. 예시의 꺾쇠괄호 값은 필드 설명이다.

```json
{
  "header": {
    "format": "gpuchain-keystore",
    "version": 1,
    "keyType": "Ed25519",
    "address": "<64 lowercase hex>",
    "origin": "bip39-slip10",
    "path": "m/1196447043'/0'"
  },
  "kdf": {
    "name": "scrypt",
    "N": 131072,
    "r": 8,
    "p": 1,
    "salt": "<16 bytes>"
  },
  "wrappedKey": { "nonce": "<12 bytes>", "ciphertext": "<32 bytes>", "tag": "<16 bytes>" },
  "signingKey": { "nonce": "<12 bytes>", "ciphertext": "<32 bytes>", "tag": "<16 bytes>" }
}
```

1. **서명 키 암호화.** 지갑마다 난수 32바이트로 데이터 암호화 키(DEK)를 만든다. DEK와 새 난수 12바이트 nonce로 서명 시드 32바이트를 AES-256-GCM 암호화해 `signingKey`를 만든다. 인증 부가 데이터(AAD)는 `UTF8(canonical(["gpuchain/signing-key/v1", header]))`이다.
2. **비밀번호로 DEK 보호.** 사용자가 정한 비어 있지 않은 파일 비밀번호를 NFC 정규화 후 UTF-8로 인코딩한다. 앞뒤 공백을 포함한 입력을 그대로 취급한다. 난수 salt 16바이트와 표의 scrypt 값으로 32바이트 래핑 키(KEK)를 파생한다. KEK와 별도 난수 12바이트 nonce로 DEK를 AES-256-GCM 암호화해 `wrappedKey`를 만든다. AAD는 `UTF8(canonical(["gpuchain/wrapped-key/v1", header, kdf, signingKey]))`이다.
3. **직렬화 및 입력 제한.** 주소 외 바이너리 필드는 패딩 없는 정규 Base64url로 기록한다. `canonical`은 기존 GPUChain의 키 정렬 JSON 인코더다. 읽기 단계에서 파일을 4 KiB로 제한하고, 중복·미정의 필드, 잘못된 길이·인코딩, 다른 버전·경로·KDF 설정을 거부한 뒤 scrypt를 실행한다. `origin`의 다른 허용 값은 아래의 `imported-ed25519`이며 이때 `path`는 JSON `null`이다. GCM 태그는 양쪽 모두 16바이트로 고정한다.
4. **잠금 해제.** 비밀번호로 KEK를 파생하고 DEK와 서명 시드를 순서대로 복호화한다. 두 인증 태그를 모두 확인한 뒤 시드에서 계산한 주소와 헤더의 주소를 대조한다. 운영자·공급자 시작 시에는 제네시스 또는 신뢰하는 설정에서 기대한 주소도 대조한다. 모두 통과한 후에만 서명을 허용한다.

scrypt 작업 메모리는 약 128 MiB다. Node 구현의 `maxmem`은 192 MiB로 지정하고 지갑 잠금 해제를 프로세스당 한 건씩 처리한다. 이 비용은 키를 열 때 발생하며 추론 토큰마다 발생하지 않는다. 파일을 얻은 사람은 오프라인에서 비밀번호를 추측할 수 있으므로 길고 고유한 파일 비밀번호가 필요하다. [RFC 7914 scrypt](https://www.rfc-editor.org/rfc/rfc7914.html) · [RFC 5116 AES-GCM](https://www.rfc-editor.org/rfc/rfc5116.html#section-5.2) · [Node.js scrypt](https://nodejs.org/docs/latest-v24.x/api/crypto.html#cryptoscryptpassword-salt-keylen-options-callback)

## 일상 사용과 복구

| 상황 | 절차와 결과 |
|---|---|
| 주소 조회·입금 | 공개 주소만 있으면 된다. 잠긴 파일의 헤더도 읽을 수 있다. 수취 주소를 처음 공유할 때는 소유자가 확인해 둔 공개 주소와 대조한다. |
| 송금·추론 정산 | 사용자는 로컬 비공개 입력으로 지갑을 열고 거래에 서명한다. 공급자·시퀀서는 시작 시 담당 키만 열고 프로세스 종료나 명시적 잠금 때 해제한다. 재시작 시에는 다시 잠긴다. 무인 실행을 붙일 경우 운영체제 비밀 저장소나 상속된 비밀 입력 채널을 사용한다. 명령행 인자·로그·일반 설정·채팅에는 비밀을 넣지 않는다. |
| 파일 비밀번호 변경 | 기존 파일을 열어 확인하고, 새 비밀번호·새 salt·새 래핑 nonce로 DEK를 다시 감싼다. 주소와 서명 키는 그대로다. 이전에 복사한 파일은 당시 비밀번호로 계속 열리므로 비밀번호 변경으로 유출된 사본을 무효화할 수 없다. |
| 새 PC에서 복구 | **새 형식으로 생성한 지갑**은 24단어로 같은 서명 키를 재생성한다. 기록해 둔 공개 주소와 일치하면 새 비밀번호, DEK, salt, nonce로 파일을 만든다. 또는 암호화 파일 사본과 해당 비밀번호로도 열 수 있다. 복구한 주소를 기존 네트워크의 신뢰된 제네시스에 연결하면 그 원장의 잔액을 쓸 수 있다. 시퀀서의 원장 DB 복구에는 별도의 상태 백업이 필요하다. |
| 비밀번호나 백업 분실 | 새 지갑은 문구가 있으면 파일과 비밀번호를 모두 잃어도 복구된다. 문구를 잃어도 암호화 파일과 비밀번호가 있으면 서명할 수 있다. 파일에는 자식 키만 저장하므로 그 파일을 열어 원래 문구를 다시 표시하는 기능은 없다. 두 복구 경로를 모두 잃으면 서명 권한을 되찾을 수 없다. |

복구 문구 자체가 서명 권한이다. 누군가 문구를 보거나 실행 중인 서명 프로세스를 장악한 상황은 저장 파일 암호화의 보호 범위를 벗어난다. 구현은 가능한 범위에서 임시 비밀 버퍼를 지우고 해제하되, JavaScript 런타임의 모든 복사본에서 완전 삭제된다고 가정하지 않는다.

## 기존 평문 지갑 이전

기존 GPUChain 지갑은 독립적으로 생성된 Ed25519 PKCS#8 키를 보유한다. 해당 키의 32바이트 시드를 추출하고, 기존 파일에 적힌 주소와 계산한 주소가 모두 일치할 때 그 시드를 암호화한다. 헤더에는 `origin = "imported-ed25519"`, `path = null`을 기록한다. **이전 지갑의 복구 수단은 암호화된 파일 백업과 당시 비밀번호**다. 새 24단어를 발급해 기존 주소를 복구할 수 있다고 표시하면 안 된다.

이전은 같은 디렉터리의 새 파일에 배타적으로 기록한다. 운영체제별 소유자 전용 접근 권한을 적용하고, 동기화 후 다시 열어 주소와 시험 서명 검증을 마친다. 완료된 파일을 원자적으로 게시하고 중단·동시 실행 시 기존 사본을 보존한다. 비밀번호 변경에도 같은 검증과 원자적 교체를 적용한다. 이전 성공과 백업 확인 후 소유자가 기존 평문 사본을 정리한다. 기존 SSD·동기화 폴더·백업에 이미 남은 평문 사본에는 각각 별도 처리가 필요하다.

## 구현 검수 기준

- **상호운용성.** 공개 시험 벡터로 영문 `abandon` 23개 다음에 `art`를 붙인 24단어, 빈 BIP39 추가 패스프레이즈, 위 고정 경로를 사용하면 주소는 `36f1f6d80f670d490550ff7522acc3b621756651878705406a5ed4099731837e`여야 한다. 누구나 아는 시험용 키다.
- **무결성.** 비밀번호 오류, 주소·키 출처 변조, 다른 파일의 슬롯 교체, nonce·암호문·태그 1바이트 변경은 모두 서명 전에 실패해야 한다. 과도한 KDF 값은 메모리 할당 전에 거부해야 한다.
- **복구와 호환성.** 문구 복구, 파일 복구, 비밀번호 변경, 기존 키 이전 후 동일 공개 주소 및 기존 원장 서명 규칙을 검증한다. 잘못 입력했지만 체크섬이 맞는 다른 문구는 기대 주소 대조에서 걸러야 한다.
- **저장 실패.** 생성·이전·교체 도중 프로세스가 끝나도 마지막으로 온전한 지갑 사본이 남아야 한다. 잠금 해제 실패나 서비스 재시작이 새 키의 자동 발급이나 평문 저장으로 이어져서는 안 된다.
